# 8. Bold is a generated table, not a runtime double-strike

Status: accepted

## Context

The Ui face is drawn bold by widening each stem. The obvious implementation is
the classic one: draw the glyph twice, the second pass offset one pixel to the
right. It costs nothing and needs no extra data.

It also produces wrong letters. At this size the interior gaps in `m`, `w`, `M`
and `W` are exactly one pixel wide, and a one-pixel smear closes them. Bold `m`
became a solid block, so the hub read "Contract ter■inal" and the depth readout
showed "58■" instead of "58 m". Capital `W` did not fill solid but lost its
shape, so "Wide Fracture Head" read as "Nide Fracture Head".

The first fix was a smarter runtime rule: widen a stem unless the pixel to its
right has ink on the far side of it, which preserves a one-pixel counter. That
fixed `m` and `M`. It did not fix `W`, because a bold `W` has three stems and,
in a six-column cell, three two-pixel stems do not fit at all.

## Decision

Two things:

1. The Ui cell is **seven columns**, not six. Advances are derived per glyph
   from its own ink, so a wider cell costs nothing in layout — only `W` and `M`
   actually use the seventh column.
2. Bold is a **second table generated by `tools/content_gen/gen_font.py`**. The
   generator widens every glyph with the counter-preserving rule above, and a
   small `BOLD_OVERRIDE_UI` dictionary replaces the handful the rule still
   spoils with hand-drawn art.

`Draw::text` selects a table. There is no runtime emboldening at all.

## Consequences

- Correct letterforms, and fewer draw calls than the double-strike it replaced,
  since bold is now one pass rather than two.
- Roughly 850 extra bytes of constant data per face. Irrelevant.
- The failure mode moved somewhere better. A bad bold glyph is now visible in
  the generator's own output and in the generated header, at authoring time,
  rather than only in a screenshot of a running game.
- Anyone editing a glyph must re-run `gen_font.py`; the header is generated and
  says so on its first line. If a bold form looks wrong after an edit, the fix
  is an entry in `BOLD_OVERRIDE_UI`, not a change to the drawing code.
- A hand override is a maintenance liability — it can drift from the regular
  weight it is supposed to match. It is kept to the two glyphs that genuinely
  need it, and every other glyph stays mechanically derived so the two weights
  cannot disagree.
- General lesson, recorded because it cost real time: this was found by reading
  a screenshot at 1:1 and misreading it twice — once as a missing glyph, once as
  a correct glyph. Cropping and magnifying the pixels settled it in seconds.
  Verify rendering by looking at pixels, not at a scaled-down page.
